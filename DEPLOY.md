# Deploying Formatly

One web service on Render, one Postgres on Supabase, no disk. Both free.

Nothing that matters is kept on the filesystem — documents, their version
history, accounts and composed drafts are all rows — so a host that wipes the
disk on every deploy is fine. What is left on it is regenerated output: an
exported `.docx`, a rendered chart.

---

## 1. The database, on Supabase

1. **Create a project** at <https://supabase.com>. Choose a region near your
   readers and set a database password — you will need it in a moment, and it
   is not shown again.

2. **Take the connection string.** In the project: **Connect** (or Project
   Settings → Database). You are offered more than one, and the difference
   matters:

   | | Port | Use it when |
   |---|---|---|
   | **Transaction pooler** | 6543 | **Start here.** Reachable over IPv4, which is what most hosts give you |
   | Session pooler | 5432 | A pooler too, one connection per session |
   | Direct connection | 5432 | Only where the host has IPv6 egress |

   A free Supabase project's *direct* connection is reachable over IPv6 only.
   If the service starts and cannot reach the database, this is almost always
   why — use the pooler.

3. **Put your password into it**, replacing `[YOUR-PASSWORD]`. The result looks
   like:

   ```
   postgresql://postgres.abcdefghijklm:PASSWORD@aws-0-eu-central-1.pooler.supabase.com:6543/postgres
   ```

   `postgres://` is fine too — it is rewritten on the way in.

There is nothing to create inside the database. Every table is made on first
start, and making them again is a no-op, so a restart and a redeploy are the
same thing to it.

> Formatly turns psycopg's prepared statements off, because they do not survive
> a pooler in transaction mode. You do not have to configure anything for this;
> it is only worth knowing if you see `prepared statement does not exist`
> somewhere else in your own code.

## 2. The service, on Render

1. Push this repository to GitHub.
2. In Render: **New → Blueprint**, point it at the repository. It reads
   [`render.yaml`](render.yaml) and proposes one web service.
3. Fill in the two secrets it asks for:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Supabase string from step 1 |
   | `MISTRAL_API_KEY` | your key — or leave it empty, see below |

   `DOCOS_SECRET` is generated by Render and kept. Do not set it by hand unless
   you have a reason: a new value on each restart logs everybody out.

4. Deploy. The first build installs LibreOffice and takes several minutes;
   later ones reuse the layers.

Render gives the service a URL. That one URL is the whole app — the API serves
the page it answers, so there is no second deployment and no CORS to configure.

---

## 3. Check it

```bash
curl https://your-service.onrender.com/health
```

Then open the URL, create an account, and upload a `.docx`. If the document
survives a redeploy, the database is wired up correctly — that is the whole
point of the exercise.

---

## What runs without what

Each of these loses one capability, not the app:

| Missing | Effect |
|---|---|
| `MISTRAL_API_KEY` | Instructions are answered by the rules instead of the planner. Most land; the panel says which answered, rather than pretending |
| LibreOffice | No Exact view and no PDF download. Everything else, including the `.docx`, is unaffected |
| `DATABASE_URL` | Falls back to a SQLite file — right on a laptop, wrong on a host with no disk |

---

## Things worth knowing before you rely on it

- **A free Render service sleeps** after about fifteen minutes idle and takes
  ~30 seconds to wake. The first request after a quiet night is slow.
- **A free Supabase project pauses** after about a week of no activity and has
  to be resumed from the dashboard.
- **512 MB of memory is enough**, measured: 128 MB idle, 386 MB peak importing,
  editing and exporting a forty-page paper. PDF conversions are serialised
  precisely so that several at once cannot exhaust it.
- **Back up the database, not the disk.** Supabase does this for you; the point
  is that there is nothing on the disk to lose.

## Running it yourself instead

One machine, one command, everything in the container:

```bash
export DOCOS_SECRET=$(python -c "import secrets; print(secrets.token_urlsafe(32))")
docker compose up -d --build     # http://localhost:8000
```

That arrangement keeps SQLite on a named volume — no Postgres involved. See
[`docker-compose.yml`](docker-compose.yml).
